§ 01

The Bet

Git was for code. Flow is for the docs AI agents produce.

Settled
The interchange format between AI work steps should be the same artifacts humans already review at work — specs, plans, decision records, postmortems, RFCs.

Not graphs, not opaque agent state, not JSON traces. Markdown documents a senior engineer or PM would recognize at a glance. This is a 20-year-stable bet, because the artifacts predate AI.

Settled
Humans must be able to inspect, edit, and resume from any step in the pipeline.

Inspection without modification is theater. If a human can read a doc but not fix it and continue, the loop is closed and the human is decoration.

§ 02

The Problem

Settled
Current flow has too many surface options and too much accidental opinionation.

The Makefile sprawls. The stages are hard-coded for code work. Users can't compose their own pipelines for non-code domains. The product became a pipeline instead of a pipeline factory.

Leaning
Existing AI workflow tools (LangGraph, evomap, hermes, DevSwarm) compete on orchestration, evolution, and autonomy.

None of them own the human-readable doc layer. They treat documents as side effects. Flow's wedge is to invert that — documents are the substrate, skills are the producers.

§ 03

The Principle

A flow is a chain of (skill, doc-type) pairs. The doc-types are the product.

Settled
Flow is a documentation expert, not an LLM and not a skill-improver.

Flow's value is knowing what kind of doc belongs between skill A and skill B. Skills are external (Claude Code skills, or whatever). LLMs are external. Skill quality is somebody else's problem.

Settled
Every stage emits a doc. Every doc is a resume point.

This single mechanic gives us audit trail, human review, fork-and-restart, and archival — without inventing new concepts.

§ 04

What Flow Is

Leaning
Flow is a pipeline-builder CLI.

Users assemble their own pipelines from skills and doc-types. Flow does not ship "the one true pipeline" — it ships the construction kit and the doc-type catalog.

Leaning
A flow is a linear chain. Forks happen by starting a new flow from a checkpoint doc, not by branching mid-flow.

DAGs were considered and rejected for v1. They add graph editing, cycle detection, parallel execution, and visualization burden — for a capability (forking) that linear-plus-checkpoint gives us for free.

Leaning
Two execution modes, one toggle: spike and step.

Spike runs end-to-end, never pauses, produces a spike log. Step pauses at every doc for human review, edit, or abort. This collapses the "too many make options" complaint into one axis: trust vs review.

Leaning
Each flow compiles to two generated skills: flow-{name}-spike and flow-{name}-step.

Source of truth is a flow definition (likely flow.yaml). The generated skills carry a "do not edit" header. Editing a flow means editing the source and regenerating.

§ 05

How It Works

Leaning
The atomic unit is a (skill, doc-type) pair.

Flow does the binding between an external skill and a doc-type from the catalog. Skills stay agnostic — they don't need to know about flow. This preserves the boundary that lets flow remain a substrate.

Leaning
Checkpoint trail lives under .flow/runs/<flow>/<timestamp>/.

Numbered files like 01-spec.md, 02-plan.md, 03-findings.md. Resume via flow resume <run-id> --from <NN>. Edit any file before resuming to fork the run.

flow new          # interactive: pick skills and doc-types
flow list         # show defined flows
flow edit <name>  # edit the source flow definition
flow rm <name>    # delete a flow

# generated skills are invoked through Claude Code:
/flow-build-feature-spike
/flow-build-feature-step
§ 06

The Moat — A Community of Doc-Types

Builder CLIs are commodity. A curated, contributable catalog of human-readable doc-types is not.

Leaning
A doc-type is a markdown file with frontmatter — purely descriptive, no runtime.
---
name: spec
purpose: capture intent before planning — what + why, not how
audience: human reviewer, downstream plan skill
shape: problem / goals / non-goals / constraints / open-questions
lifecycle: append-only; supersedes prior specs
maturity: stable
---
[template body with section guidance]
[1-2 example docs]

This is the contribution unit. Markdown plus frontmatter. No DSL, no execution semantics. Anyone who can write a good design doc can contribute.

Leaning
Ship a bootstrap catalog of 6-8 doc-types, then open contribution.
  • spec — intent
  • plan — steps
  • findings — review output
  • decision-record — why we chose X
  • spike-log — what was tried, what we learned
  • change-summary — what shipped, for PR description

Each is hand-tested in real work before launch. That's the credibility floor.

Open
Community model: start with a GitHub repo + PR-based contributions. Move to a CLI registry only if usage demands it.

Three options ranked: (1) GitHub repo — lowest friction, ship now; (2) CLI registry with versioning and namespacing — feels like a real ecosystem, more infra; (3) Curated only — defeats the moat thesis. Default to (1).

Risk to name

Communities don't form because the product is good. They form because a recognizable group is already using it in public and writing about it. Distribution is the actual work — and it's not bundled with the code.

§ 07

What Flow Is Not

Settled
Flow does not improve skills, host LLMs, or evaluate output quality.

Skill evolution belongs to the user, to evomap, to hermes, or to whatever comes next. Flow stays out of the agent arms race so it can be the substrate they all depend on.

Leaning
Flow does not ship opinionated pipelines for specific domains.

The current code-pipeline cell becomes a starter template, not the product. Other pipelines are user-built. Flow ships the kit, not the work.

§ 09

Open Questions — Push Here

Open · catalog governance

Who reviews PRs to the doc-type catalog? Solo curation (high quality, no scale) vs maintainer pool (scales, drifts) vs tag-based namespaces (jliang/spec vs official/spec)? This decision shapes whether the moat is a personal canon or a community standard.

Open · source format

Is the flow definition flow.yaml, a markdown file with frontmatter, or generated entirely through interactive prompts with no human-edited source? The doc-as-source approach is on-brand but adds parsing weight.

Open · skill discovery

How does flow know what skills exist? Reads ~/.claude/skills? Project-local .claude/skills? Both? Cross-tool (also read from Cursor, Cline, etc.)? The answer determines portability.

Open · the "what doc belongs here" decision

Is binding (skill ↔ doc-type) chosen by the user at flow-creation time, or inferred by flow based on the doc-type catalog's metadata? The latter is more "documentation expert" — but it's also where flow could quietly become opinionated again.

Open · distribution wedge

What's the first public artifact that gets people in? A blog post walking through a real flow with the full doc trail visible? A demo video? A live registry page? Pick the one we can ship in a week.

§ 10

First Moves

  1. Author the bootstrap catalog — 6-8 doc-types, written as proper markdown templates with examples. Test each one in a real flow before publishing.
  2. Write one founding blog post at jasonliang.com: a real flow run with the complete doc trail visible. Title candidate: "What my AI workflow leaves behind."
  3. Strip the runtime to the kernel — remove the embedded code-pipeline opinions from the core. Make it a starter cell, not the product.
  4. Ship flow new as the interactive builder. Linear chains only. Generate spike and step skills as output.
  5. Stand up flow-doc-types repo on GitHub with the bootstrap catalog and a clear contribution README. Accept first external PR before building any registry infra.
